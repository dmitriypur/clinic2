# План рефакторинга блоковой системы

## Цель документа
Этот документ нужен как единая рабочая карта для поэтапного и безопасного рефакторинга блоковой системы сайта.

Работа по нему ведётся в отдельной ветке:
- `codex/block-refactor-plan`

Главный принцип:
- не делать большой рефактор одним проходом;
- каждый этап должен быть изолированным, проверяемым и откатываемым;
- не менять внешний контракт блоков без отдельного решения;
- не ломать уже созданный контент в админке.

## Текущее состояние
Сейчас блоковая система работает, но стала тяжёлой в сопровождении:
- растёт число `BlockType`;
- `app/Filament/Resources/BlockResource.php` перегружен условной логикой;
- в `app/Models/Block.php` есть повторяющаяся подготовка данных для media-driven блоков;
- `resources/views/components/block.blade.php` стал большим dispatcher-файлом;
- паттерны hero/media/items повторяются в разных вариантах.

При этом система уже в продакшен-используемом состоянии, поэтому рефакторинг должен идти без массовых контрактных изменений.

## Правила безопасности
Перед каждым этапом:
1. Работать только из отдельной ветки.
2. Не смешивать несколько архитектурных изменений в одном коммите.
3. Не менять сразу и backend-структуру, и payload, и frontend-шаблоны для целого семейства блоков.
4. Не переименовывать существующие `payload`-ключи, media collections и `BlockType`, если в этом нет отдельной необходимости.
5. После каждого этапа обновлять `docs/APP_CONTEXT.md`.

Общее правило выполнения:
1. Один маленький этап.
2. Локальная проверка.
3. Фиксация результата.
4. Только потом следующий шаг.

## Что не трогаем на ранних этапах
Пока сознательно не трогаем:
- сохранённые структуры `payload` у существующих блоков;
- названия media collections;
- общий механизм page/block rendering целиком;
- миграции по блочной системе;
- объединение нескольких уже используемых `BlockType` в один универсальный тип;
- радикальную смену Vue/Blade-подхода.

Это отложенные шаги. Их можно обсуждать только после безопасной расчистки текущего кода.

## Этапы рефакторинга

### Этап 1. Инвентаризация и фиксация семейств блоков
Цель:
- описать, какие блоки относятся к одним и тем же паттернам.

Что сделать:
- сгруппировать block types по семействам:
  - hero/banner;
  - text + image;
  - items/cards;
  - apparatus family;
  - faq/accordion;
  - media-only blocks;
  - service/doctor-driven blocks.
- для каждого семейства зафиксировать:
  - какие поля реально повторяются;
  - какие шаблоны уже можно считать базовыми;
  - какие block types пока остаются уникальными.

Результат:
- короткая карта повторов, по которой можно безопасно рефакторить дальше.

Риск:
- низкий.

Изменения в коде:
- минимальные или отсутствуют.

### Этап 2. Разделение `BlockResource` на приватные schema-методы
Цель:
- уменьшить размер и хрупкость `app/Filament/Resources/BlockResource.php` без изменения поведения.

Что сделать:
- вынести повторяющиеся секции формы в приватные методы внутри `BlockResource`;
- разнести по методам:
  - общие поля блока;
  - media fields;
  - button fields;
  - hero fields;
  - apparatus items;
  - repeaters для items/elements/faq;
  - shared text/image sections.

Важно:
- не менять имена полей;
- не менять payload-структуру;
- не менять visibility-логику по существу;
- только структурировать код.

Результат:
- файл становится читаемее;
- добавление новых блоков становится менее рискованным.

Риск:
- низкий, если не трогать ключи и условия.

Проверка:
- открыть несколько уже сделанных сегодня блоков в админке;
- проверить, что поля по-прежнему видимы и сохраняются корректно.

### Этап 3. Упрощение `Block` model через внутренние helper-методы
Цель:
- убрать повторяющуюся подготовку `responsive_image` / `image_html`.

Что сделать:
- вынести общую механику подготовки item-массивов в приватный helper внутри [app/Models/Block.php](/Applications/MAMP/htdocs/zrenie.clinic-7/app/Models/Block.php);
- использовать этот helper для:
  - `getElementsAttribute()`;
  - `getServicesAttribute()`;
  - `getApparatusTreatmentSectionsAttribute()`;
  - `getApparatusMethodsItemsAttribute()`;
  - других похожих accessor’ов, если контракт совпадает.

Важно:
- не менять имена accessor’ов;
- не менять выходную структуру массивов;
- не менять conversion names и collection names на этом этапе.

Результат:
- меньше дублирования;
- проще отлаживать media-driven блоки;
- ниже риск разъезда логики между похожими блоками.

Риск:
- низкий или средний.

Проверка:
- фронтенд страниц с `elements`, `services`, `apparatus-*` блоками;
- изображения должны отображаться без изменений.

### Этап 4. Нормализация паттернов админских repeaters
Цель:
- унифицировать способ хранения повторяющихся item-структур.

Что сделать:
- определить повторяющиеся типы repeaters:
  - `title + text`;
  - `title + body_html + image`;
  - `text only`;
  - `question + answer`.
- где возможно, собирать их через повторно используемые schema-builder helpers.

Важно:
- это не миграция данных;
- это только унификация конфигурации Filament.

Результат:
- новые контентные блоки собираются быстрее;
- меньше шанс, что похожий блок снова получит новую уникальную форму без необходимости.

Риск:
- низкий.

### Этап 5. Аудит и ограничение media conversions
Цель:
- уменьшить лишнюю генерацию conversion’ов для модели `Block`.

Что сделать:
- проверить текущие conversions в [app/Models/Block.php](/Applications/MAMP/htdocs/zrenie.clinic-7/app/Models/Block.php);
- определить, какие из них должны работать только для конкретных collections;
- аккуратно добавить `performOnCollections(...)` там, где это безопасно.

Важно:
- этот этап чувствительный;
- нельзя менять его до проверки, какие шаблоны реально используют конкретные conversion names.

Результат:
- меньше лишней генерации изображений;
- понятнее медиа-пайплайн для новых блоков.

Риск:
- средний.

Проверка:
- повторная загрузка тестовых изображений в блоки;
- проверка responsive/webp output на уже используемых шаблонах.

### Этап 6. Карта рендера блоков вместо разросшегося `@switch`
Цель:
- упростить `resources/views/components/block.blade.php`.

Что сделать:
- сначала зафиксировать существующие типы и целевые partials;
- затем заменить giant `@switch` на более управляемый registry-подход:
  - либо map в PHP;
  - либо helper/метод, который возвращает view для block type.

Важно:
- это делать только после стабилизации `BlockResource` и `Block.php`;
- не смешивать с payload-рефактором.

Результат:
- меньше центральной хрупкости;
- проще добавлять новые блоки без правки большого switch.

Риск:
- средний.

Проверка:
- smoke-check по нескольким страницам с разными типами блоков.

### Этап 7. Нормализация family-patterns для новых блоков
Цель:
- перестать делать “один новый макет = один новый подход”.

Что сделать:
- пройтись по семейству `APPARATUS_*`;
- определить, что из этого уже стало reusable-паттерном;
- зафиксировать, какие поля и шаблонные решения являются базовыми:
  - disease cards;
  - methods accordion/cards;
  - treatment sections;
  - hero variants;
  - tasks note-box.

Результат:
- следующие блоки этого семейства будут делаться через существующие схемы, а не через новые импровизации.

Риск:
- средний, если затронуть уже сохранённый контент;
- низкий, если ограничиться только документацией и локальными helper-методами.

## Порядок выполнения
Рекомендуемый фактический порядок:

2. Этап 2
3. Этап 3
4. Проверка
5. Этап 4
6. Проверка
7. Этап 5
8. Проверка
9. Этап 6
10. Этап 7

Не переходить к следующему крупному шагу, если предыдущий не стабилизирован.

## Формат работы по документу
Для каждого этапа делать:
1. Отдельный маленький коммит.
2. Короткое обновление `docs/APP_CONTEXT.md`.
3. Краткую запись в этом документе:
   - что сделано;
   - что отложено;
   - какие риски остались.

Можно дополнять этот документ секциями:
- `Статус`;
- `Сделано`;
- `Осталось`;
- `Риски`.

## Критерии “сделано хорошо”
Рефакторинг считается удачным, если:
- не меняется поведение уже созданных блоков;
- не ломается админка Filament;
- не меняются payload-ключи без отдельной причины;
- новые блоки можно добавлять быстрее и чище;
- код в `BlockResource` и `Block.php` становится заметно проще читать;
- дальнейшие улучшения можно делать локально, а не через массовую переделку.

## Следующий практический шаг
Первый реальный шаг после создания этого документа:
- выполнить Этап 1 и Этап 2;
- то есть сначала зафиксировать семейства блоков, а затем безопасно разнести `BlockResource` на приватные schema-методы без изменения поведения.
