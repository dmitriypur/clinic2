# Реестр блоков и генератор новых типов

## Статус

Проект дизайна для первого безопасного этапа. Реализация начинается после подтверждения документа.

## Цель

Сделать добавление нового типа блока локальной и предсказуемой операцией:

- новый тип создаётся одной Artisan-командой;
- его форма, Blade-шаблон и подготовка данных находятся рядом;
- `BlockResource` перестаёт расти за счёт новых условных секций;
- центральный Blade `@switch` перестаёт расти;
- существующие записи `blocks` продолжают работать без миграции и изменения структуры данных.

## Не входит в первый этап

- перенос всех существующих типов блоков;
- изменение таблиц или сохранённых `payload` / `settings`;
- изменение числовых значений `BlockType`;
- перенос существующих model accessors и media conversions;
- создание или редактирование Blade-кода через production-админку;
- удаление `BlockResource` или управления блоками внутри страниц;
- автоматическое обновление `docs/APP_CONTEXT.md`.

## Текущее состояние

Описание одного типа блока распределено между несколькими местами:

- `app/Enums/BlockType.php` хранит числовой тип и подпись;
- `app/Filament/Resources/BlockResource.php` содержит общие и специфичные поля всех типов;
- `resources/views/components/block.blade.php` выбирает Blade-компонент через большой `@switch`;
- `app/Models/Block.php` содержит часть специфичной подготовки данных и media;
- отдельный Blade-файл отображает блок.

Новый простой блок обычно требует правок нескольких центральных файлов. Из-за этого растёт вероятность задеть соседний тип и получить конфликт изменений.

## Общий подход

Новая система вводится рядом со старой. Перенесённые и новые типы обслуживаются реестром, остальные продолжают работать через существующую реализацию.

```text
BlockType
   |
   v
BlockRegistry ---- определение найдено ----> BlockDefinition
   |                                      /       |       \
   |                                     label   schema   view
   |
   +---- определения нет ----> legacy form / legacy @switch
```

Это позволяет переносить типы небольшими группами и в любой момент остановиться без массовой переделки.

## BlockDefinition

Каждый перенесённый тип получает самостоятельный definition-класс в `app/Blocks/Definitions`.

Definition сообщает системе:

- соответствующий `BlockType`;
- подпись в админке;
- Blade-view;
- специфичную Filament-схему;
- при необходимости дополнительные данные для view.

Базовый контракт должен иметь минимальный обязательный набор. Подготовка дополнительных данных имеет реализацию по умолчанию и не требуется простым блокам.

Поля формы продолжают использовать текущие пути, например `payload.items` и `payload.image_position`. Definition не вводит новый формат хранения.

## BlockRegistry

`BlockRegistry` является единой точкой поиска definition по `BlockType`.

На первом этапе список классов хранится в небольшом явном конфигурационном реестре. Это предпочтительнее сканирования файловой системы при каждом запросе:

- результат детерминирован;
- работает с `config:cache`;
- легко проверяется тестом;
- генератор сам добавляет новую запись, поэтому разработчик не редактирует реестр вручную.

Реестр обязан отклонять дублирующиеся типы и definition с несовпадающим `BlockType`.

## Совместимость с BlockType

`BlockType` остаётся backed enum с текущими integer-значениями. Значения существующих cases не меняются.

Для перенесённого типа подпись может приходить из definition. Для остальных типов продолжает работать существующий `getLabel()`.

Новый тип по-прежнему получает enum case, потому что поле `blocks.type` и model cast сохраняются. Добавление case выполняет генератор. Миграция БД для этого не требуется.

## Интеграция с BlockResource

Форма делится на три части:

1. Общая схема: страница, города, тип, заголовок, якорь, фон и настройки отображения.
2. Definition-схема: поля выбранного перенесённого типа.
3. Legacy-схема: существующие поля ещё не перенесённых типов.

После выбора типа `BlockResource` спрашивает `BlockRegistry` о definition. Если definition найден, подключается его схема. Если нет — остаётся текущая legacy-логика.

При переносе конкретного типа его старые поля удаляются из legacy-секции, чтобы в форме не появлялись два компонента с одинаковым state path.

Имена полей, правила обязательности, значения по умолчанию, media collection names и dehydrated-поведение сохраняются без изменений.

## Интеграция с рендерингом

Общая секция `resources/views/components/block.blade.php` продолжает отвечать за:

- внешний `<section>`;
- фон и отступы;
- видимость на устройствах;
- breadcrumbs;
- заголовок страницы.

Перед legacy `@switch` выполняется поиск definition:

- если definition найден, подключается указанный им view;
- если definition отсутствует, выполняется текущий `@switch`.

После полного переноса всех типов legacy `@switch` можно удалить отдельным этапом. В первый этап это не входит.

## Подготовка данных

Definition может вернуть дополнительные данные для Blade, но в первом этапе существующие accessors и media-логика модели не перемещаются.

Это ограничение специально уменьшает риск: первый этап меняет только регистрацию, форму и выбор view, но не контракт данных между моделью и шаблоном.

Перенос model accessors в отдельные presenters/providers возможен позднее, отдельными изменениями и тестами.

## Команда make:block

Команда имеет интерфейс вида:

```bash
php artisan make:block "Этапы лечения"
```

Дополнительные options позволяют явно задать enum name и slug, если автоматическое значение не подходит.

Команда:

1. строит `TREATMENT_STEPS`, `TreatmentStepsDefinition` и `treatment-steps`;
2. находит следующий свободный integer `BlockType`;
3. проверяет конфликты enum name, integer, класса и view;
4. добавляет enum case в обозначенную точку генерации;
5. создаёт definition из stub;
6. создаёт Blade-view из stub;
7. создаёт тестовую заготовку;
8. регистрирует definition;
9. выводит список созданных файлов и следующие действия.

Команда должна завершаться без частичных изменений при конфликте. Повторный запуск с теми же параметрами не перезаписывает существующие файлы.

После генерации разработчик заполняет только definition-схему, Blade и тест.

## Пилотные типы

Первым этапом в реестр переносятся три недавно добавленных и уже покрытых тестами типа:

- `RECEPTION_STEPS`;
- `DIAGNOSTIC_METHODS`;
- `TREATMENT_METHODS`.

Они дают проверку простого repeater-блока и блоков с более сложной структурой, не требуя массового переноса.

## Админка

Создание новых типов блоков в админке не добавляется.

Управление экземплярами блоков внутри страниц сохраняется. Решение о скрытии отдельного глобального пункта «Блоки» принимается позднее после проверки, используется ли он в рабочем процессе. Оно не связано с реестром и не входит в первый этап.

## База данных

Первый этап не содержит migrations.

Не меняются:

- `blocks.type`;
- enum values существующих типов;
- `blocks.payload`;
- `blocks.settings`;
- media collections;
- связи со страницами и городами;
- order и visibility-настройки.

Переключение ветки само по себе не изменяет данные. Проверки сохранения выполняются на test database или копии рабочей БД, но не на production.

## Проверки

Обязательные автоматические проверки:

- каждый зарегистрированный definition ссылается на уникальный `BlockType`;
- каждый зарегистрированный view существует;
- registry возвращает definition для пилотных типов и `null` для legacy-типа;
- подписи и options для типов сохраняются;
- HTML пилотных блоков до и после переноса эквивалентен;
- формы пилотных блоков используют прежние state paths;
- команда создаёт полный набор файлов;
- команда не перезаписывает существующие файлы;
- текущие блочные feature tests продолжают проходить.

Ручная проверка на копии данных:

- открыть и сохранить по одному экземпляру каждого пилотного типа;
- сравнить `payload`, `settings` и media до и после сохранения;
- проверить страницы в разных городах;
- проверить добавление, сортировку и удаление блока внутри страницы;
- проверить desktop и mobile render.

## Этапы реализации

1. Контракт definition, registry и coverage tests.
2. Registry-aware render с legacy fallback.
3. Registry-aware form с legacy fallback.
4. Перенос трёх пилотных типов без изменения их контрактов.
5. Artisan generator и его tests.
6. Фокусные тесты и ручной smoke-check на копии данных.

Каждый этап должен быть отдельным логическим коммитом или как минимум отдельной проверяемой частью diff.

## Откат

Так как миграций нет, откат выполняется возвратом кода на предыдущую ревизию.

До полного переноса legacy form и `@switch` сохраняются. При проблеме definition конкретного типа можно удалить из реестра и вернуть его старую ветку формы/render без изменения данных.

## Критерии готовности первого этапа

- новые типы можно создавать командой;
- три пилотных типа работают через registry;
- остальные типы продолжают работать через legacy fallback;
- центральные файлы больше не требуют новых type-specific вставок для типов, созданных генератором;
- migrations отсутствуют;
- существующие integer type values и payload-контракты не изменены;
- автоматические блочные тесты проходят;
- пользовательские `.DS_Store` и другие посторонние изменения не входят в коммиты.

## Оценка объёма и риска

Первый этап — разработка умеренного объёма. Основная сложность находится в динамической Filament-схеме и надёжном генераторе, а не в базе данных.

Полный перенос всех существующих типов был бы крупной разработкой и не входит в эту итерацию. Постепенная схема даёт основную пользу сразу и сохраняет контролируемый риск.
