# Рефакторинг и улучшения: рекомендации (2026-05-12)

Документ фиксирует результаты технической оценки приложения и приоритетный план улучшений.
Это read-only аудит: в рамках оценки код не менялся.

## Контекст

- Проект: Laravel 10 + Blade + Vue 2.7 + Vite + Tailwind + Filament 3.
- Особенности: мультигород, интеграции с UNF, отдельный booking API, контентная блоковая система.
- Цель: зафиксировать технические риски и последовательность рефакторинга без смены стека.

## Краткий вывод

Приложение рабочее и уже содержит сильные решения (особенно по booking API и мультигороду), но есть накопленный технический долг:

1. Публичные уязвимые/технические маршруты.
2. Устаревающая платформа (Laravel 10 / Vue 2.7).
3. Неравномерное качество интеграционных слоев (legacy `Clinic` vs новый booking service).
4. Разросшиеся узлы сложности: блоковая система и `BookingWidgetV3`.
5. Фрагментированная кеш-стратегия.

## Приоритеты (в порядке выполнения)

## 1) Закрыть публичный `/clear-price` (срочно)

Проблема:
- Есть публичный маршрут сброса кеша без авторизации.

Где:
- `routes/web.php` (`/clear-price`).

Рекомендация:
- Удалить публичный endpoint.
- Перенести в artisan-команду или admin-действие под `auth:staff`.

Ожидаемый эффект:
- Устранение риска внешнего сброса кешей и деградации производительности.

## 2) Исправить логику поиска по активным страницам

Проблема:
- В поиске `where('active', 1)` логически не сгруппирован с `orWhere`, из-за чего возможна выдача неактивного контента.

Где:
- `app/Http/Controllers/SearchController.php`.

Рекомендация:
- Сгруппировать условия через вложенный `where(function (...) { ... })`.
- Добавить feature-тест на исключение inactive-страниц.

Ожидаемый эффект:
- Корректная выдача и снижение риска регрессий SEO/контента.

## 3) Усилить rate limit для публичных форм/API

Проблема:
- Сейчас в основном действует общий лимит API, но чувствительные точки не имеют явных целевых ограничителей.

Где:
- `app/Providers/RouteServiceProvider.php`.
- `routes/api.php` (`/callback`, `/making-an-appointment`, `/send-verification-code`, `/review`).

Рекомендация:
- Ввести отдельные limiter-профили для форм (по IP/телефону/эндпойнту).
- Применить точечно middleware `throttle:<name>`.

Ожидаемый эффект:
- Меньше риска abuse/spam и нагрузочных всплесков.

## 4) Привести legacy `Clinic` к стандарту нового booking API

Проблема:
- Legacy интеграция (`Clinic`) статическая и менее защищенная: нет единообразной обработки ошибок/таймаутов/retry.

Где:
- `app/Clinic.php`.
- Контроллеры форм/записи: `CallbackController`, `MakingAnAppointmentController`, `FormController`.

Рекомендация:
- Вынести UNF-взаимодействие в сервис с контрактом.
- Добавить timeout/retry/structured logging/обработку неуспешных ответов.
- Сделать единый формат ошибок для frontend.

Ожидаемый эффект:
- Повышение отказоустойчивости интеграции и управляемости инцидентов.

## 5) Вынести тяжелую бизнес-логику из `routes/web.php`

Проблема:
- В `routes/web.php` живет значимый runtime-код (sitemap closure, динамический regex для городов и fallback-ветки).

Где:
- `routes/web.php`.

Рекомендация:
- Вынести `sitemap.xml` в контроллер.
- Упростить route constraints городов и снизить зависимость от БД при регистрации маршрутов.

Ожидаемый эффект:
- Предсказуемый bootstrap роутинга и меньше edge-case логики в routes-файле.

## 6) Довести рефактор блоковой системы поэтапно

Проблема:
- Ключевые файлы слишком крупные, высокая стоимость изменений:
  - `app/Filament/Resources/BlockResource.php` (~1554 строк).
  - `app/Models/Block.php` (~625 строк).
  - `resources/views/components/block.blade.php` (крупный dispatcher).

Где:
- См. также существующий план: `docs/block-refactor-plan.md`.

Рекомендация:
- Идти малыми этапами из плана:
1. Декомпозиция schema в `BlockResource`.
2. Выделение helper-методов в `Block`.
3. Нормализация repeaters.
4. Упрощение dispatcher-а рендера блоков.
- Не менять payload/media contracts без отдельного миграционного шага.

Ожидаемый эффект:
- Снижение хрупкости админки и упрощение добавления новых блоков.

## 7) Разгрузить `BookingWidgetV3` без смены стека

Проблема:
- `BookingWidgetV3.vue` очень большой (~2505 строк), много состояния и переходов в одном компоненте.

Где:
- `resources/js/components/BookingWidgetV3/BookingWidgetV3.vue`.
- Косвенно: `resources/js/app.js`.

Рекомендация:
- Вынести flow-state, кеширование и трансформации данных в отдельные JS-модули/сервисы.
- Сохранять Vue 2.7 и текущие контракты API.
- Добавить/расширить тесты для критичных переходов (direct doctor/clinic/date flow).

Ожидаемый эффект:
- Проще сопровождать фичи записи, меньше риск регрессий в шагах.

## 8) Унифицировать кеш-стратегию

Проблема:
- Разные TTL/ключи/инвалидация в PageService/Controller/Models и legacy-ключах.

Где:
- `PageController`, `PageService`, модели `Page/Block/Doctor/Review/Promotion/City` и связанные observers.

Рекомендация:
- Описать единый стандарт ключей и источников инвалидации.
- По возможности использовать tags (если драйвер поддерживает).
- Убрать лишние legacy-ключи после валидации обратной совместимости.

Ожидаемый эффект:
- Предсказуемость кешей, меньше «случайных» stale-данных.

## 9) Обновить `.env.example` до актуальных интеграций

Проблема:
- Не все критичные env-переменные отражены в шаблоне окружения.

Где:
- `.env.example`.
- `config/zrenie-clinic.php`, `config/services-integration.php`.

Рекомендация:
- Добавить недостающие ключи (`UNF_BASE_URL`, `CLINIC_UUID`, `LO_TOKEN`, `BOOKING_API_BASE_URL`, `SMS_AERO_*` и т.д.).
- Кратко пояснить обязательность/дефолты.

Ожидаемый эффект:
- Быстрее и безопаснее поднимать окружения, меньше конфигурационных ошибок.

## 10) Upgrade-дорожная карта платформы (отдельным треком)

Проблема:
- Laravel 10 и Vue 2.7 — зона повышенного техдолга по поддержке.

Рекомендация:
- Вести upgrade отдельной веткой и отдельным планом:
1. PHP target-версия.
2. Обновление Laravel на поддерживаемую ветку.
3. Стратегия фронтенд-эволюции без «большого взрыва».

Ожидаемый эффект:
- Контролируемый переход без смешивания с продуктовой разработкой.

## Ограничения выполнения

- Не менять текущий стек без отдельного согласования.
- Не ломать мультигород-контракты и городские привязки.
- Не менять payload-структуры блоков без миграционного плана.
- Делать изменения малыми, проверяемыми порциями.
