# BookingWidgetV3: Ветка Выбора По Дате

Документ фиксирует согласованный план для следующей доработки `BookingWidgetV3`: отдельной ветки записи `по дате`.

План написан так, чтобы после возврата к задаче можно было сразу приступать к реализации без повторного анализа требований.

## Цель

Добавить в `BookingWidgetV3` новый сценарий записи:
- пользователь выбирает режим `по дате`;
- затем вводит дату рождения пациента;
- затем попадает на шаг с календарём;
- на выбранную дату видит список врачей, у которых есть расписание на этот день и которые подходят по возрасту пациента.

Список врачей на этом шаге должен обновляться при смене даты.

## Общий Flow

Целевой путь:

1. `start`
2. `birth-date`
3. `date-select`
4. `doctor-schedule` или специализированный шаг выбора времени
5. `form`
6. `success`

Важно:
- шаг `birth-date` общий и используется всеми ветками виджета;
- новая ветка `date` должна подключаться после `birth-date`, а не до него;
- логика шага `birth-date` уже должна быть спроектирована так, чтобы после него можно было маршрутизировать:
  - в `doctor-flow`
  - в `clinic-flow`
  - в `date-flow`

## Что Должно Быть На Шаге Выбора По Дате

Шаг `date-select` должен содержать:
- календарь;
- активную текущую дату по умолчанию;
- список врачей, у которых есть доступное расписание на выбранную дату;
- карточку врача с:
  - фото;
  - ФИО;
  - специальностью;
  - филиалом.

При смене даты:
- список врачей должен сразу перестраиваться;
- должны показываться только врачи, у которых на эту дату есть доступные слоты и которые проходят возрастную фильтрацию.

## Обязательная Возрастная Фильтрация

Ветка `по дате` должна использовать ту же age-логику, что и остальные сценарии виджета.

Источник истины:
- `extra.age_min_months`
- `extra.age_max_months`

Правила:
- если у врача задан `age_min_months`, пациент должен быть не младше этого значения;
- если у врача задан `age_max_months`, пациент должен быть не старше этого значения;
- если заданы обе границы, должны выполняться обе проверки;
- если задана только одна граница, проверяется только она;
- если не задано ни одной границы, врач не отсекается по возрасту.

Следствие:
- врач `до 17 лет` не должен показываться для пациента 18 лет;
- врач `с 2 лет` не должен показываться для младенца;
- врач без верхней границы проверяется только по нижней;
- врач без нижней границы проверяется только по верхней.

## Как Должна Работать Дата

Дата рождения пациента:
- вводится на шаге `birth-date`;
- хранится в root-state виджета;
- используется для фильтрации врачей;
- в финальной форме автоподставляется и может быть отредактирована пользователем.

Дата записи:
- выбирается на шаге `date-select`;
- по умолчанию активна текущая дата;
- при смене даты обновляется список врачей.

Итог:
- дата рождения определяет, какие врачи вообще допустимы;
- дата записи определяет, у кого из этих врачей есть расписание в этот день.

## Что Нельзя Делать Во Фронтенде

Нельзя строить ветку `по дате` через плохой N+1-сценарий:
- загрузить всех врачей;
- затем для каждого врача отдельно запрашивать его слоты на дату;
- потом на клиенте собирать итоговый список.

Такой подход:
- даст много лишних запросов;
- будет тормозить при смене даты;
- усложнит кеширование;
- ухудшит UX.

## Что Нужно От API

Для этой ветки API нужно расширить.

Текущего API достаточно для:
- doctor-flow;
- clinic-flow.

Но для `date-flow` нужен агрегирующий endpoint, который сразу отдаёт:
- только подходящих врачей;
- только на выбранную дату;
- с учётом даты рождения пациента;
- с информацией о филиале.

Рекомендуемый контракт:

`GET /api/v1/cities/{city_id}/doctors-by-date?date=YYYY-MM-DD&birth_date=YYYY-MM-DD`

Дополнительно можно поддержать:
- `clinic_id`
- `branch_id`

Ответ должен содержать список сущностей уровня `doctor-on-date`, а не просто “голых врачей”.

Минимальный состав полей:
- `doctor_id`
- `full_name`
- `speciality`
- `avatar`
- `clinic_id`
- `clinic_title`
- `branch_id`
- `branch_title`
- `first_available_slot`
- `available_slots_count`

Почему так:
- один врач может быть доступен в разных филиалах;
- карточка должна показывать филиал;
- шаг выбора по дате работает не просто со “врачом”, а с “врачом в филиале на дату”.

## Где Лучше Реализовать Агрегацию

Предпочтительный путь:

1. Если можно менять внешний booking API:
   - добавить новый endpoint туда.

2. Если внешний API менять нельзя:
   - сделать у нас server-side агрегирующий endpoint/proxy в Laravel;
   - он будет:
     - получать данные из booking API;
     - применять age filtering;
     - собирать итоговый список врачей на дату;
     - отдавать фронтенду уже готовый payload.

Для best practice второй вариант тоже нормальный, если сделать его как отдельный сервисный слой, а не как ad hoc-логику внутри Vue.

## Архитектура На Фронтенде

Новый сценарий должен быть реализован как отдельная ветка `date-flow`, а не как “случайный режим” внутри текущих doctor/clinic шагов.

Нужны:
- новый mode, например `date`;
- новый шаг `date-select`;
- отдельный transport method в `bookingApi`;
- отдельный mapping/filtering util для списка `doctor-on-date`.

Важно сохранить разделение ответственности:
- `start` — выбор сценария;
- `birth-date` — сбор даты рождения;
- `date-select` — выбор даты записи и показ доступных врачей;
- `form` — финальная форма;
- `success` — успешная запись.

## Поведение Карточки На Шаге По Дате

Карточка врача должна показывать:
- фото;
- ФИО;
- специальность;
- филиал.

При выборе карточки пользователя нужно вести дальше в привычный сценарий выбора времени.

Рекомендуемое поведение:
- выбранная карточка открывает следующий шаг с доступными слотами именно этого врача, именно на уже выбранную дату.

То есть дальше:
- не нужно повторно выбирать дату;
- дата уже зафиксирована из шага `date-select`;
- остаётся выбрать время.

## Последний Шаг Формы

Поле даты рождения в `PatientFormStep`:
- остаётся;
- автозаполняется из шага `birth-date`;
- может быть вручную изменено;
- не является местом первичной фильтрации списка врачей.

Поле даты записи:
- должно уже быть определено из `date-select`;
- на последнем шаге не должно ломать уже выбранный сценарий.

## Empty State

Если на выбранную дату нет подходящих врачей:
- список карточек пуст;
- показывается понятное сообщение;
- пользователь может:
  - выбрать другую дату;
  - вернуться назад;
  - изменить дату рождения.

Рекомендованный смысл текста:
- `На выбранную дату подходящих специалистов не найдено`

## Что Должно Быть Подготовлено Заранее

Перед реализацией этой ветки желательно, чтобы уже существовали:
- общий шаг `birth-date`;
- root-state с датой рождения пациента;
- локальная age filtering logic по `age_min_months/age_max_months`;
- единый util для преобразования даты рождения;
- понятная структура routing внутри `BookingWidgetV3` по mode.

## Acceptance Criteria

Фича считается сделанной, если:

1. В стартовом шаге есть сценарий `по дате`.
2. После выбора этого сценария пользователь сначала вводит дату рождения.
3. Затем открывается шаг с календарём.
4. Текущая дата активна по умолчанию.
5. При смене даты перестраивается список врачей.
6. В списке показываются только врачи:
   - с доступным расписанием на выбранную дату;
   - подходящие по возрасту пациента.
7. Карточка врача показывает:
   - фото;
   - ФИО;
   - специальность;
   - филиал.
8. После выбора врача пользователь не выбирает дату повторно, а идёт к выбору времени.
9. Поле даты рождения в финальной форме уже заполнено из шага `birth-date`.
10. Реализация не построена на фронтенд-N+1 запросах по каждому врачу.

## Краткое Пояснение Для Быстрого Возврата К Задаче

Нужно сделать третий сценарий виджета: не `по врачу` и не `по клинике`, а `по дате`.

Сначала пользователь вводит дату рождения пациента, потом выбирает дату записи, и видит только тех врачей:
- кто подходит по возрасту;
- у кого есть расписание на этот день.

Для этой ветки нужен отдельный агрегирующий API-ответ “врачи на дату”, потому что собирать это на фронтенде по одному врачу через слоты — плохая архитектура.
