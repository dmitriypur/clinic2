# AGENTS.md

Этот файл задаёт постоянные инструкции для ассистента в данном репозитории.

## Порядок работы
1. Сначала прочитать этот `AGENTS.md`.
2. Если пользователь пишет «Продолжаем работу» или явно просит продолжить технический аудит/сопровождение:
   - прочитать только `.maintenance/STATUS.md`;
   - затем прочитать только файл из поля «Текущая задача»;
   - открывать лишь исходники и тесты, перечисленные в этой задаче или непосредственно связанные с ними;
   - не читать заново `README_AI_TASK.md`, roadmap, полный аудит и другие документы, если текущая задача прямо этого не требует;
   - до любых действий сообщить название задачи, рекомендуемые модель и уровень reasoning из карточки задачи; дождаться переключения модели или явного подтверждения работы на текущей;
   - после работы обновить статус и карточку задачи;
   - в итоговом сообщении обязательно дать одну готовую фразу для рабочего отчёта: одно предложение, понятное руководителю без технических деталей и соответствующее фактически выполненной работе.
   - перед тем как указать следующую задачу в `STATUS.md`, сначала создать и проверить её карточку; если путь из `STATUS.md` отсутствует, создать карточку по roadmap автоматически, а не запрашивать путь у пользователя.
3. Во всех остальных случаях затем прочитать `README_AI_TASK.md`.
4. Не читать `docs/APP_CONTEXT.md` по умолчанию.
5. Читать `docs/APP_CONTEXT.md` только по прямой просьбе пользователя, например: «Изучи документ `docs/APP_CONTEXT.md`, тему ...».
6. При необходимости открыть связанные документы из `docs/*`, кроме `docs/APP_CONTEXT.md`, если пользователь не попросил его явно.
7. Каждую задачу с изменением кода выполнять в отдельной ветке `feature/<task-id>-<краткое-название>`. Перед началом реализации проверить текущую ветку и рабочее дерево:
   - если уже открыта соответствующая ветка задачи — использовать её;
   - если открыта `main` и рабочее дерево чистое — создать ветку задачи от локального `main`;
   - если открыта другая ветка или есть непонятные изменения — не переключать и не сбрасывать их, попросить пользователя определить дальнейшие действия.
8. После завершения задачи, тестов и smoke-проверки не выполнять commit или merge автоматически. Сначала дать итог, одно предложение для рабочего отчёта и спросить явное разрешение: «Можно закоммитить изменения в ветке <branch> и влить её в main?»
9. После явного разрешения закоммитить изменения в ветке задачи и влить её в локальный `main`. Push не выполнять: пользователь делает его самостоятельно.
10. Если мы создаем новую ветку для разработки и при этом находимся не в основной main, нужно закоммитить все изменения в текущей и влить ее в main, но не сразу а после подтверждения разработчика, то есть сначала уточнить этот шаг.

## Режим работы
- Писать кратко и по делу.
- Если задача понятна из кода и конфигурации, не задавать лишних вопросов.
- Не пересказывать большие куски кода в чате без необходимости.
- После изменений давать короткий отчёт: что сделано и в каких файлах.
- Не обновлять `docs/APP_CONTEXT.md` автоматически после правок. Обновлять его только по прямой просьбе пользователя.

## Экономия контекста и токенов
- По умолчанию читать только целевые файлы и ближайший связанный код.
- Не выводить большие `diff`, логи, дампы или документы в чат без прямой просьбы пользователя.
- Для логов и ошибок читать только релевантный фрагмент, обычно последние 30–50 строк или строки вокруг ошибки.
- Использовать `rg`/точечный `sed` вместо чтения больших файлов целиком.
- Запускать тесты точечно через `--filter`, если задача не требует полного test-suite.
- Не запускать `npm run build`, если правка backend-only и сборка frontend не нужна для проверки.
- Не делать browser-smoke, SSH-проверки и внешние проверки без необходимости или прямой просьбы.
- Не смешивать несколько независимых тем в одну диагностику; держать фокус на текущей задаче.

## Технический контекст проекта
- Backend: `Laravel 10`.
- Frontend: `Blade + Vue 2.7 + Vite + TailwindCSS`.
- Admin: `Filament 3` + `Filament Shield` + `Filament Navigation`.
- Основной сайт поддерживает мультигород через URL-префикс и cookies.
- Есть внешняя интеграция с UNF API и отдельное integration API для услуг.

## Ограничения
- Не менять стек без явной задачи.
- Не переписывать проект на Inertia, Vue 3, React или другой frontend-стек.
- Не ломать существующую мультигород-логику, кеши и привязки контента к городам.
- Не удалять существующие документы в `docs/`, если задача не требует консолидации.

## Живой контекст проекта
- `docs/APP_CONTEXT.md` — большой контекст проекта, который читается и обновляется только по прямой просьбе пользователя.
- Если пользователь попросил обновить `docs/APP_CONTEXT.md`, минимум проверить и при необходимости исправить:
  - `Что изменилось (последнее)`
  - `Журнал изменений`
  - `Маршруты`
  - `Сервисы и интеграции`
  - `Env и конфигурация`
  - `Ограничения и замечания`
